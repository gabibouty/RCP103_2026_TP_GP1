\begin{abstract}
    Ce TP a pour objectif de créer un programme permettant de simuler un système simple de type Client(s)/Serveur asynchrones. Ce simulateur nous permettra de réaliser des mesures variées pour qualifier notre système (nombre instantané de requêtes, temps d'attente, etc.), sans avoir à mettre en œuvre concrètement ce dernier.
    Ce premier document présente l'initialisation du projet, la schématisation du simulateur, et la description de la réalisation des premiers composants.
\end{abstract}

\section{Description du système simulé}

Comme évoqué en introduction, ce rapport présente la première phase de réalisation d'un simple simulateur à évènements discrets du type Client(s)/Serveur:

Un ensemble de $N$ clients ($N \geq 1$), envoient des messages à 1 serveur. Un portail sert d'intermédiaire entre les clients et le serveur. Compte tenu que le serveur ne peut traiter qu'un message à la fois, le portail permet de temporiser les messages en attente de traitement dans une file de taille fixe $K$.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.80\textwidth]{../images/system.png}
    \caption{Schéma du système simulé}
\end{figure}

Dans ce simulateur, les envois de messages suivent un processus de Poisson: le taux d'envois est constant dans le temps, les temps entre deux envois consécutifs suivent une distribution exponentielle. De même, le temps de service suit une loi exponentielle.

Compte tenu du fait que nous n'avons pour l'instant qu'un seul serveur, nous pouvons donc définir cette simulation comme un processus de file d'attente de type M/M/1/K:

\begin{itemize}
    \item M: Arrivées selon un processus de Poisson (Markovien).
    \item M: Temps de service selon une distribution exponentielle (Markovien).
    \item 1: Nombre de serveurs (ici, 1).
    \item K: Capacité du système (ici, la taille de la file du portail de capacité K).
\end{itemize}

La configuration du simulateur est définie comme suit:

\begin{itemize}
    \item Temps moyen inter-message: configurable
    \item Temps de transmission: $1t$
    \item Temps moyen de service: configurable
    \item Temps total de la simulation: configurable
\end{itemize}

\section{Architecture du simulateur}
\subsection{Architecture initiale}

Afin de simuler les transmissions et traitement de messages entre le ou les \emph{Client} et le \emph{Server} (à travers le \emph{Gateway}), chaque étape de gestion du \emph{Message} sera encapsulée dans des \emph{Event}. Ces \emph{Event} pourront être, de fait, de 3 types différents:

\begin{itemize}
    \item \lstinline|SEND_MSG|: Le message est envoyé par le client.
    \item \lstinline|RECV_MSG|: Le message est reçu par le portail.
    \item \lstinline|MSG_DPT|: Le message est transmis au serveur (si ce dernier est disponible).
\end{itemize}

Chacun de ces \emph{Event} sera timestampé et stocké chronologiquement dans un ordonnanceur (\emph{Scheduler}). Ainsi, en itérant progressivement sur les évènements enregistrés dans le \emph{Scheduler}, nous pourrons simuler l'écoulement du temps, en nous concentrant uniquement sur les échantillons temporels qui nous intéressent.

L'ensemble de ces composants seront encapsulés dans un \emph{Engine}, dont la boucle principale viendra interagir avec ces derniers afin de dérouler la simulation.

\section{Création des premières classes}
\subsection{Les données: class Message et class Event}
Comme évoqué précédemment, la classe \emph{Message} est l'unité d'échange entre \emph{Client} et \emph{Server}.
Cette classe contient:
\begin{itemize}
    \item L'identifiant du message: \lstinline|message_id|
    \item L'identifiant du nœud émetteur: \lstinline|source|
    \item L'identifiant du nœud destination: \lstinline|destination|
    \item L'instant auquel le message est envoyé par le client: \lstinline|send_time|
    \item L'instant auquel le message arrive à la passerelle: \lstinline|arrival_time|
    \item L'instant auquel le traitement du message commence par le serveur : \lstinline|server_start|
\end{itemize}

Ce \emph{Message} est encapsulé dans un \emph{Event}, dont les attributs sont les suivants:
\begin{itemize}
    \item L'identifiant de l'évènement: \lstinline|id|
    \item Le type de l'évènement: \lstinline|type|
    \item Le timestamp de l'évènement: \lstinline|timestamp|
    \item Le \emph{Message} encapsulé: \lstinline|message|
\end{itemize}

\bigskip

\subsection{L'ordonnanceur: class Scheduler}

La classe \emph{Scheduler} est chargée de gérer les futurs évènements du simulateur. Elle contient une liste d'évènements triés par ordre chronologique.

Lorsqu'un nouvel évènement est ajouté, la méthode parcourt la liste depuis la fin afin de trouver la bonne position d'insertion. Tant que le temps de l'évènement déjà présent est supérieur au temps du nouvel évènement, on remonte la liste. Lorsque la bonne position est trouvée, le nouvel évènement est inséré avec insert. Cela permet de garder la liste triée sans utiliser \lstinline|sort| après chaque ajout.

La méthode \lstinline|pop_event| retire et retourne le premier évènement de la liste. Comme la liste est maintenue triée par temps d'exécution, cet évènement correspond toujours au prochain évènement à traiter.

La méthode \lstinline|get_current_time| retourne le temps du premier évènement de la liste, c'est-à-dire le temps courant du simulateur. Si la liste est vide, la méthode retourne 0.

Enfin, la méthode \lstinline|has_events| permet de savoir s'il reste encore des évènements à traiter.

\bigskip

\subsection{Les fonctions de logs: functions Trace}

Le module \lstinline|trace| contient trois fonctions fournissant un système de journalisation au simulateur, permettant de visualiser et d'enregistrer les évènements.

Voici le prototype et la description de chaque fonction :

\lstinline|def get_time_and_node(e: Event)|:  prend un évènement en paramètre et retourne un tuple constitué du numéro de nœud et du temps en fonction du type d'évènement.

\lstinline|def generateTraceOut(t_event: list[Event])|:  prend une liste d'évènements en paramètre et écrit sur la sortie standard l'ensemble des évènements contenu dans la liste.

\lstinline|def generateTraceCSV(t_event: list[Event])|: prend une liste d'évènements en paramètre et écrit dans un fichier nommé \lstinline|trace.csv| l'ensemble des évènements contenu dans la liste au format CSV. Le délimiteur utilisé est le caractère '\lstinline|;|'.

\bigskip

\subsection{Le cœur du système: class Engine}

La classe \emph{Engine} représente le cœur du simulateur. Elle définit les instances des différents composants (Client(s), Serveur, etc.) lors de son initialisation, et simule les transactions entre chacuns d'entre eux durant l'exécution de la simulation.

Comme cette classe repose sur les imlémentations des autres composants, elle ne préente, pour l'heure, que peu d'intêret. Cependant, elle expose d'ores et déjà ses principales fonctionnalitées, à savoir l'initialisation, et la boucle d'exécution.

\bigskip

\subsection{Le point d'entrée: function main}

Le point d'entrée du programme se trouve dans \lstinline|tp02_main.py|. Il permet d'executer le programme simplement en appelant \lstinline|python tp02_main.py| depuis le répertoire racine.

En l'état, il se contente de créer une instance d'\emph{Engine},
et de lancer l'execution de cette instance. Mais on pourrait par exemple imaginer y ajouter un parsing d'arguments pour configurer le simulateur dynamiquement.

\section{Tests des premières classes}
\subsection{Le système de test: Pytest}
Afin de vérifier le bon fonctionnement des classes implémentées, des tests unitaires ont été réalisés avec l'aide de l'utilitaire \lstinline|Pytest|. L'objectif est de tester chaque classe séparément avant de l'intégrer dans le simulateur. L'ensemble des tests sont regroupés dans le répertoire \lstinline|tests|.

\bigskip
\bigskip

\subsection{Présentation des tests rédigés}

Test de \emph{Message}:
\begin{itemize}
    \item Le test \lstinline|test_message| vérifie que le constructeur initialise correctement les attributs du message (l'identifiant, la source et la destination, temps).
    \item Le test \lstinline|test_message_setters| vérifie que les setters modifient correctement les valeurs internes de l'objet, après modification de l'identifiant, de la source, de la destination, et des différents temps, les getters sont utilisés pour vérifier que les nouvelles valeurs ont bien été enregistrées.
    \item Le test \lstinline|test_message_str| vérifie la méthode d'affichage de la classe message. Cette méthode est utile pour le débogage, car elle permet d'afficher rapidement les informations principales d'un message.
\end{itemize}

\bigskip

Test de \emph{Event}:
\begin{itemize}
    \item Le test \lstinline|test_event_init| vérifie que le constructeur initialise correctement le temps de l'événement et son type. Un événement de type \lstinline|SEND_MSG| est créé avec un temps égal à 1.5, puis les getters permettent de vérifier que ces valeurs sont bien stockées.
    \item Le test \lstinline|test_event_setters| vérifie que le temps et le type d'un événement peuvent être modifiés correctement. Par exemple, un événement initialement de type \lstinline|SEND_MSG| est modifié en \lstinline|RECV_MSG|, et son temps est changé de 5.5 à 8.0.
    \item Le test \lstinline|test_event_message_content| vérifie que l'événement conserve bien le message qui lui est associé. Après avoir récupéré le message depuis l'événement, le test vérifie que son identifiant, sa source et sa destination sont corrects.
    \item Le test \lstinline|test_event_str| vérifie la méthode d'affichage de la classe \emph{Event}. Cette méthode affiche l'identifiant de l'événement, son type, son temps et le message associé. Elle permet donc de faciliter le suivi des événements.
\end{itemize}

\bigskip

Test de \emph{Scheduler}:
\begin{itemize}
    \item Le test \lstinline|test_sheduler| vérifie que les temps des événements récupérés sont toujours dans l'ordre chronologique croissant. Cela permet de valider le rôle principal du \emph{Scheduler} : maintenir les événements futurs triés par temps d'exécution.
\end{itemize}

\bigskip

Test de \emph{Trace}:
\begin{itemize}
    \item Le test définit par \lstinline|test_get_time_and_node_event_SEND_MSG| vérifie que la fonction \lstinline|get_time_and_node_event| renvoie bien le bon tuple en fonction du type de message.
    \item Le test définit par \lstinline|test_get_time_and_node_event_RECV_MSG| vérifie que la fonction \lstinline|get_time_and_node_event| renvoie bien le bon tuple en fonction du type de message.
    \item Le test définit par \lstinline|test_get_time_and_node_event_MSG_DEPT| vérifie que la fonction \lstinline|get_time_and_node_event| renvoie bien le bon tuple en fonction du type de message.
    \item Le test définit par \lstinline|test_generateTraceOut_SEND_MSG(capsys)| vérifie que la fonction \lstinline|generateTraceOut| affiche les bonnes informations en fonction du type de message.
    \item Le test définit par \lstinline|test_generateTraceOut_RECV_MSG(capsys)| vérifie que la fonction \lstinline|generateTraceOut| affiche les bonnes informations en fonction du type de message.
    \item Le test définit par \lstinline|test_generateTraceOut_MSG_DEPT(capsys)| vérifie que la fonction \lstinline|generateTraceOut| affiche les bonnes informations en fonction du type de message.
    \item Le test définit par \lstinline|test_generateTraceCSV| vérifie que la fonction \lstinline|generateTraceCSV| crée le fichier "trace.csv" avec les bonnes valeurs pour plusieurs messages.
\end{itemize}

\bigskip

Test de \emph{Engine}:
\begin{itemize}
    \item Le test \lstinline|test_engine_complete| vérifie que l'exécution du \lstinline|run| de \emph{Engine} ne tombe pas dans une boucle sans fin, et que l'ensemble des \emph{Message} et \emph{Event} sont bien consommés à l'issue de l'exécution.
\end{itemize}

\bigskip

\subsection{Exécution des tests}
Les tests peuvent être lancés depuis le répertoire principal en tapant la commande \lstinline|pytest| (attention, \lstinline|Pytest| doit être préalablement installé).
L'ensemble des tests présents dans le répertoire \lstinline|tests| seront exécutés.

\section{Conclusion}
Cette première partie du TP nous permet d'appréhender ce que peut être un simulateur à évènements discrets. Nous mettons en œuvre des concepts vus en cours tels que les files d'attente ou encore les processus de Poisson.

Il nous permet aussi de comprendre l'intérêt que peut représenter la complémentarité qu'il peut exister entre modélisation mathématique et simulation. En effet, la modélisation mathématique nous fournit les outils (variables aléatoires, processus stochastiques, etc.) qui vont nous permettre de construire facilement un simulateur, et ainsi réaliser, tout aussi facilement, des mesures sur un système complexe. Établir et mettre en œuvre un protocole de mesures sur ce même système dans le monde réel aurait été bien plus lourd et couteux.

Cette première itération dans la réalisation du simulateur, nous a permis de préparer les premiers composants nécessaires à son bon fonctionnement. Même si ces composants sont amenés à être plus ou moins modifiés au cours des prochaines itérations, le développement de tests unitaires sur chacune des briques logicielles nous permettra de confirmer en continue la validité de ces dernières, mais aussi d'éviter les régressions lors des futures étapes de développement.
